# DairyFarm demo on GCP

This configuration deploys DairyFarm separately from other applications in
the account. It uses Cloud Run, Cloud SQL for PostgreSQL, Artifact Registry,
Secret Manager, and a private GCS Terraform state bucket. Cloud Run exposes
the UI and read-only API after the synthetic dataset has been loaded.

## Design and cost posture

- The API and Nginx UI are separate Cloud Run services, both scale to zero,
  and are capped at two instances by default.
- Cloud SQL uses the lowest-cost shared-core tier by default, one zone, one
  retained backup, and no point-in-time recovery. It is a demo-sized database,
  not a high-availability production tier, and it has an ongoing monthly cost.
- Cloud SQL is scheduled to run from 4:30 a.m. to 6:00 p.m.
  `America/Los_Angeles`. Starting early allows for database startup time;
  the app should be available by 5:00 a.m. The approximate 13.5-hour daily
  compute window saves about 44% of always-on database compute, not half the
  entire bill: storage, backups, registry, state bucket, and other costs
  remain.
- Cloud SQL has a public IP for the managed Cloud Run connector, but no
  authorized networks are configured. The app connects through Cloud Run's
  Cloud SQL integration; database credentials are not exposed on the network.
- Django and database credentials are generated by Terraform and exposed to
  Cloud Run through Secret Manager. Terraform state also contains those
  generated values, so protect the private GCS state bucket and never publish
  state files or plans.
- The app uses per-instance in-memory caching on Cloud Run instead of adding a
  separately billed cache service. It keeps Memcached when
  `MEMCACHED_LOCATION` is configured, as it is in local Compose.
- The public API is directly invokable as well as proxied through the UI. Its
  public permission policy must remain read-only and scoped to the synthetic
  farm. When the database is stopped, the UI proxy serves a friendly
  maintenance page for database-related server errors.

## Prerequisites and authentication

Use a **dedicated GCP project** with billing enabled; do not point this at
another application's Terraform-managed resources. The Google Terraform
provider uses Application Default Credentials (ADC), matching the access
pattern in the referenced GCP Terraform configuration. It does not read a
service-account key file from this repository.

```sh
gcloud auth login
gcloud auth application-default login
gcloud config set project YOUR_DEDICATED_PROJECT_ID
```

The identity needs permission to enable the required APIs, create project IAM
bindings, and create Cloud SQL, Cloud Run, Secret Manager, Artifact Registry,
and GCS resources. `gcloud auth configure-docker` is also used to push images.

## One-time state bucket

The bootstrap module uses local state because it creates the bucket needed by
the main configuration's remote backend:

```sh
cd terraform/gcp/bootstrap
cp terraform.tfvars.example terraform.tfvars
# Edit terraform.tfvars and set the dedicated project ID.
terraform init
terraform plan
terraform apply
```

Review the plan before applying. Capture the bucket name, then initialize the
main stack's GCS backend:

```sh
STATE_BUCKET="$(terraform output -raw state_bucket_name)"
cd ..
terraform init -backend-config="bucket=${STATE_BUCKET}" \
  -backend-config="prefix=dairyfarm/gcp"
cp terraform.tfvars.example terraform.tfvars
# Edit terraform.tfvars with the same dedicated project ID.
```

The bootstrap bucket has uniform bucket-level access, public access prevention,
object versioning, and deletion protection.

## Deploy

Run each Terraform apply from `terraform/gcp`. The first apply creates the
managed database, registry, secrets, and runtime identity, but no public web
services:

```sh
terraform plan -var="deploy_workloads=false" -var="public_access=false"
terraform apply -var="deploy_workloads=false" -var="public_access=false"
```

Build and push both images. Use the stable `production` tag so Terraform and
the GitHub Actions pipeline refer to the same image tag. Cloud Run revisions
retain the resolved image digest:

```sh
REGION=us-central1
REPOSITORY="$(terraform output -raw artifact_registry_repository)"
TAG=production

gcloud auth configure-docker "${REGION}-docker.pkg.dev"
docker build -f Dockerfile -t "${REPOSITORY}/api:${TAG}" .
docker push "${REPOSITORY}/api:${TAG}"
docker build -f docker/ui/cloudrun.Dockerfile \
  -t "${REPOSITORY}/ui:${TAG}" .
docker push "${REPOSITORY}/ui:${TAG}"
```

Create the Cloud Run services and the still-private database initialization
job. Then execute the job to migrate PostgreSQL and load only the reviewed
synthetic dataset:

```sh
terraform apply \
  -var="image_tag=${TAG}" \
  -var="deploy_workloads=true" \
  -var="public_access=false"

JOB_NAME="$(terraform output -raw initialization_job_name)"
gcloud run jobs execute "${JOB_NAME}" \
  --region "${REGION}" --wait
```

Inspect the job's completed execution and logs. Only after it succeeds, grant
public invocation to the UI and read-only API:

```sh
terraform plan \
  -var="image_tag=${TAG}" \
  -var="deploy_workloads=true" \
  -var="public_access=true"
terraform apply \
  -var="image_tag=${TAG}" \
  -var="deploy_workloads=true" \
  -var="public_access=true"

terraform output -raw ui_service_url
```

The generated Cloud Run URL provides HTTPS. The Django settings enable
production mode, secure cookies, HTTPS redirects, and a one-day initial HSTS
policy. Revisit HSTS after a custom domain is selected. Set up billing alerts
and review current GCP pricing before applying; budgets notify but do not cap
charges.

## Resource and cost checks

Run the deployment smoke test before or after granting public access:

```sh
./verify-demo-gcp.sh --private
./verify-demo-gcp.sh --public
```

Use `--private` while Cloud Run IAM restricts the API to authenticated
invokers. Use `--public` after enabling anonymous read-only access. The script
checks the visible farm, cow count and farm-local numbering, blocked login and
writes, the public UI/read-only bootstrap, a static asset, and the HTTPS HSTS header.

After applying the stack, run the live resource check:

```sh
./check-resources-gcp.sh
```

It queries Cloud SQL, Artifact Registry, Secret Manager, service accounts, and
any deployed Cloud Run services/job. It reports PASS/FAIL for queried
resources, and skips Cloud Run checks before the workloads are deployed.

For a quick modeled cost baseline, run:

```sh
./estimate-costs-gcp.sh
```

This is an approximate list-price model, not a billing report. It estimates
Cloud SQL compute only for the default `db-f1-micro` tier and its SSD storage.
Override the assumptions with `CLOUDSQL_F1_MICRO_HOURLY` and
`CLOUDSQL_PD_SSD_GB_MONTH` if current regional prices differ. It models
13.5 Cloud SQL compute hours per day by default; override that assumption with
`DB_HOURS_PER_DAY`. It reports
Cloud Run's scale-to-zero setup but excludes actual request/CPU/memory usage,
network egress, backups, and registry/state storage. For actual costs, use
Cloud Billing reports; GCP cost reporting requires a billing export to
BigQuery before it can be queried programmatically.

## Daily availability schedule

Cloud Scheduler starts Cloud SQL at 4:30 a.m. and stops it at 6:00 p.m.
`America/Los_Angeles` daily. Starting early allows for database startup; the
demo should be ready by 5:00 a.m. The 13.5-hour compute window saves about 44%
of continuous Cloud SQL compute charges, not half of the total bill. Storage,
backups, Artifact Registry, the state bucket, and usage-based costs remain.
When Django returns a server error because the database is stopped, the UI
proxy shows `DairyFarm demo is offline` and the expected opening hours.

The schedule can be triggered manually:

```sh
gcloud scheduler jobs run dairyfarm-demo-sql-start \
  --location us-central1 --project "$(terraform output -raw gcp_project_id)"
gcloud scheduler jobs run dairyfarm-demo-sql-stop \
  --location us-central1 --project "$(terraform output -raw gcp_project_id)"
```

Check the configured schedule without changing service state, or explicitly
exercise the stop/maintenance/start flow (which temporarily takes the database
offline and may take several minutes):

```sh
./verify-schedule-gcp.sh --check
./verify-schedule-gcp.sh --exercise
```

Use the smaller wait helper whenever a database operation is still
transitioning. By default it waits for this Terraform stack's instance to be
`RUNNABLE`; the project is loaded first from `GCP_PROJECT_ID` or Terraform
output:

```sh
./wait-for-cloudsql-gcp.sh
GCP_PROJECT_ID=your-project ./wait-for-cloudsql-gcp.sh STOPPED
```

## GitHub Actions continuous deployment

The existing CI workflow continues to test pushes and pull requests. A push
to `ai-assisted` deploys only after tests pass. GitHub authenticates through
Workload Identity Federation—no service-account key is stored in GitHub.
Terraform restricts the provider to this repository and branch. The deployer
can publish images to this Artifact Registry and update the app's Cloud Run
services/jobs; it cannot change public IAM or Cloud SQL.

Validate the workflow YAML and ensure deploy remains gated on CI with:

```sh
./scripts/validate-github-workflow.sh
```

After applying the Terraform configuration, set the repository Actions
variables from `terraform/gcp`:

```sh
./configure-github-actions-vars.sh
```

## Teardown

Public access can be removed without deleting resources:

```sh
terraform apply \
  -var="image_tag=${TAG}" \
  -var="deploy_workloads=true" \
  -var="public_access=false"
```

Cloud SQL deletion protection is on by default. To intentionally destroy the
demo, first review and back up any data you need, then disable public access
and deletion protection:

```sh
terraform apply \
  -var="image_tag=${TAG}" \
  -var="deploy_workloads=true" \
  -var="public_access=false" \
  -var="database_deletion_protection=false"
terraform destroy \
  -var="image_tag=${TAG}" \
  -var="deploy_workloads=true" \
  -var="public_access=false" \
  -var="database_deletion_protection=false"
```

Keep the GCS state bucket until the stack is fully retired; deleting it is a
separate, deliberate operation.
